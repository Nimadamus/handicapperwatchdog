# Watchdog Pro: how it works and how to release it

Branch `pro-staging`. Nothing here is live. `main` (the live site) is unchanged by this branch.

## How Pro data stays private
`build.py` writes each capper's names and pick log to `data/x/<id>.bin`, encrypted with AES-GCM under its own key,
HMAC(`HWD_PRO_KEY`, 'capper:' + id). Without a key the files are random bytes. The API hands a key only to a signed
in account whose subscription is active (or past_due inside a 3 day grace), rate limited.
No names or pick rows are ever published in the clear. A subscriber gets at most 400 keys an hour per Worker instance.

## Entitlement rules
active, trialing: Pro. cancel_at_period_end: Pro until Stripe ends it. past_due: Pro until period end + 3 days.
unpaid, canceled, incomplete, incomplete_expired: free. Webhooks are verified (5 minute tolerance) and deduplicated by event id.
A live Stripe key is refused unless `BILLING_LIVE=yes`.

## Owner steps (need you)
1. **Stripe**: create a separate Stripe account for Handicapper Watchdog (business, bank and tax details are yours).
   Then give me its **test** secret key; `backend/stripe_setup.mjs` creates the product, both prices, the customer portal
   setup and the webhook endpoint, and prints the IDs to store.
2. **Cloudflare**: add handicapperwatchdog.com on the Free plan, switch nameservers at GoDaddy, create the minimum token.
   Details and free tier fit: `docs/CLOUDFLARE.md`. Then `tools/cf_setup.sh` does the rest.
3. **Email**: use the existing Brevo account (free tier, 300 emails a day, no upgrade). Add handicapperwatchdog.com as a sender
   domain in Brevo and add the DNS records it shows (at Cloudflare after step 2). The code supports Brevo and Resend.
4. **Legal**: decide the items in `docs/LEGAL_REVIEW.md` and create the support mailbox.
5. **Approve the production release.** Live billing is a separate, later approval (`BILLING_LIVE=yes` plus live keys).

## Secrets
`STRIPE_SECRET_KEY` (sk_test_ until live is approved), `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_ANNUAL`,
`STRIPE_PORTAL_CONFIG` (optional), `SESSION_SECRET` (generated by cf_setup.sh), `HWD_PRO_KEY` (random 32+ chars, also a GitHub
Actions secret so the build can encrypt Pro data), `BREVO_API_KEY`, `MAIL_FROM` (for example login@handicapperwatchdog.com).
`BILLING_LIVE` stays unset until live billing is approved.

## Release steps (after approval)
1. Merge `pro-staging` into `main` with `HWD_PRO_KEY` set as an Actions secret. The next build publishes the new pages and the
   encrypted Pro files; with no API yet, Pro buttons say "Opening soon", so this step is safe on its own.
2. Run `tools/cf_setup.sh`. Check `https://handicapperwatchdog.com/api/health` returns `"billing":"test"`.
3. Make a test purchase with card 4242 4242 4242 4242, confirm names and pick logs unlock, cancel in the portal.
4. Run `python tools/verify_live.py` (must print PASS). Run `python tools/ui_test.py` only against `backend/dev.mjs`
   before merging, never against production (it creates test subscriptions).
5. Live billing, when approved: live Stripe keys, rerun stripe_setup.mjs with `--live`, set `BILLING_LIVE=yes`.

## Tests
- `node --test backend/test.mjs`: 20 API tests.
- `node backend/e2e.mjs <dev url>`: 14 end to end steps against `backend/dev.mjs` (fake Stripe).
- `python tools/ui_test.py <dev url>`: 78 headless browser checks at desktop, tablet and phone sizes.
- `python tools/verify_live.py`: live site against the source records, leak scan.
